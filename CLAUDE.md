## 1. What this project is

A multi-module Maven monorepo simulating a payment-processing platform: account management (implemented) + an event-driven payment engine over Kafka (implemented — Avro-serialized events, Apicurio Registry-validated, account-existence checked via cache before publishing). It is a **portfolio project** aimed at demonstrating senior-level Java/Spring backend skills for an international audience — treat naming, comments, commit messages, and log output as public-facing artifacts, not throwaway dev scratch.

Root Maven coordinates: `com.joaopbessa.payments:spring-kafka-payment-processor:1.0.0-SNAPSHOT` (`pom.xml`, `packaging=pom`).

## 2. Module map

| Module | Type | Responsibility |
|---|---|---|
| `common-libraries` | jar | Shared domain primitives: `PaymentMethod` enum (Jackson-annotated, and now also carrying a mapping to its Avro-generated counterpart) plus `PaymentEvent.avsc` — the Avro schema for the Kafka payment event, compiled via `avro-maven-plugin` into `target/generated-sources/avro` (never committed) — and `ActuatorObservationAutoConfiguration`, a Spring Boot auto-configuration (registered in `META-INF/spring/…AutoConfiguration.imports`) that gives both apps the predicate keeping `/actuator*` out of HTTP metrics and traces, so neither app declares it. It also holds the security building blocks the apps share (Spring Security dependencies are optional here, each app declares its starter): `Base64PasswordEncoder` (a demonstration encoding, not a hash — see its Javadoc) behind `PasswordEncoderAutoConfiguration` (a `DelegatingPasswordEncoder`, stored values look like `{base64}...`), and `ResourceServerSecurityAutoConfiguration` (JWT resource server: roles from the `roles` claim become `ROLE_*`, `@PreAuthorize` on controller methods, `/actuator/health` open, `/actuator/prometheus` needs `METRICS_READ`, CSRF on but exempt for Bearer requests, backs off when an app declares its own `SecurityFilterChain`). Its test-jar offers `TestJwtIssuer` (key pair, decoder and signed tokens for tests). |
| `payment-db-migration` | jar (Flyway scripts + plugin config) | Owns Flyway SQL migrations (`src/main/resources/db/migration`) and the `flyway-maven-plugin` binding, decoupled from the runtime app module. Besides `ACCOUNT` and `PAYMENT` it creates `APP_USER` and `APP_USER_ROLE` (V5) and seeds four demonstration users (V6, password `<username>-demo`, stored as `{base64}...`); only the database role `payment-auth-app` can read those tables (`SELECT`, nothing else; its credentials live in the Vault secret `secret/payment-auth-server`, never in an application file). Locally the `db-migrate` compose service applies them with `payment-admin`; the apps never run Flyway (only the consumer's tests do, with this module on the test classpath). |
| `payment-producer-api` | Spring Boot app | REST API, JPA persistence, Redis cache, Vault-backed config, Avro-serialized Kafka producer. |
| `payment-consumer-api` | Spring Boot app (Actuator + DLT view and replay, an OAuth2 resource server, port 8082) | Consumes `payment.events`, persists payments to the `PAYMENT` table idempotently, retries with exponential backoff and dead-letters to `payment.events.DLT`. Has its own Vault secret (`secret/payment-consumer-api`) and database role (`payment-consumer-app`, SELECT/INSERT on `PAYMENT` only); the producer's are `secret/payment-producer-api` and `payment-producer-app` (CRUD on `ACCOUNT` only). |
| `payment-auth-server` | Spring Boot app (OAuth2 authorization server, port 9000) | Spring Authorization Server: signs people in against `APP_USER`/`APP_USER_ROLE` (authorization code + PKCE, client `payments-cli`) and issues JWTs to services (client credentials: `prometheus`, `traffic-generator`); the access token carries a `roles` claim (user roles for people, the client's configured roles for services), lives 15 minutes, no refresh token. Its own Vault secret (`secret/payment-auth-server`: database credentials and the client secrets) and database role (`payment-auth-app`, SELECT on the two user tables only). Nothing secret is in an application file (`NoCredentialsInConfigTest`); Actuator exposes only `health,info`. The signing key is the ephemeral RSA key Boot generates, so a restart invalidates issued tokens. |

Dependency direction: all three apps depend on `common-libraries`; `payment-db-migration` is only a test dependency of the consumer and the auth server. The producer is a resource server (`ResourceServerSecurityAutoConfiguration` plus `spring.security.oauth2.resourceserver.jwt.issuer-uri` for the `iss` check and `jwk-set-uri` for the keys, fetched lazily, so it starts without the auth server; do not rely on `issuer-uri` discovery alone, because the auth server serves no `/.well-known/openid-configuration` and Spring Security fails with a 500 on the login page it gets instead. With no key cached and the issuer unreachable, a request carrying a token gets a 500, one without a token a 401); the consumer is configured the same way (`issuer-uri` + `jwk-set-uri`, `security/Roles`). Prometheus and `monitoring/generate-traffic.sh` authenticate as the `prometheus` and `traffic-generator` clients (client credentials). The Spring Cloud BOM, Apicurio version and Lombok compiler config live in the root `pom.xml`.

## 3. Tech stack (as pinned in POMs, not as advertised in the README)

- **Java 21**, Spring Boot **4.0.0** (parent `pom.xml`)
- Spring Cloud **2025.1.1** (root `pom.xml`, imported as a BOM for both apps)
- Persistence: Spring Data JPA + PostgreSQL 15, Flyway migrations, dedicated `payment` schema
- Cache: Spring Data Redis + `spring-boot-starter-cache`, manual `RedisCacheManager` bean (JSON value serialization, 10-minute TTL, null-caching disabled)
- Config/secrets: Spring Cloud Vault (`spring-cloud-starter-vault-config` + `spring-cloud-starter-bootstrap`, token auth, KV v2 backend) — see `bootstrap.yml`
- Messaging: `spring-boot-starter-kafka` + Apicurio's `apicurio-registry-avro-serde-kafka` (3.0.8) client. `PaymentController` synchronously publishes Avro-encoded `PaymentEvent`s (schema in `common-libraries/src/main/avro/PaymentEvent.avsc`) to the `payment.events` topic via `PaymentService`/`KafkaProducerConfig`, backed by a single-node Kafka broker (`apache/kafka:4.1.1`, KRaft) and an Apicurio Registry (in-memory) container, both in `docker-compose.yml` (see §5)
- Observability: Actuator + `micrometer-registry-prometheus` in both apps (`/actuator/prometheus`, tag `application`), tracing via Brave exported to Zipkin with the Kafka hop propagated through Spring Kafka observation (`traceparent`), `json-logs` profile for ECS structured logs. The `/actuator*` exclusion comes from the shared `ActuatorObservationPredicate` (see §2). `docker-compose.yml` runs Prometheus, Grafana (dashboards in `monitoring/grafana/dashboards`), Zipkin and a Kafka exporter. In `@SpringBootTest` Brave only creates its propagation factory while trace export is enabled, so tests that need propagation use `@AutoConfigureTracing` and turn off only `management.tracing.export.zipkin`.
- Security: Spring Security 7 (from the Boot 4.0.0 BOM). The authorization server uses `spring-boot-starter-security-oauth2-authorization-server`; the JWT validation shared by the apps uses `spring-boot-starter-security-oauth2-resource-server` (optional in `common-libraries`, each app declares the starter). In Spring Security 7 the login adds a `FACTOR_PASSWORD` authority, so the `roles` claim is built only from `ROLE_*` authorities.
- Validation: Jakarta Bean Validation (`spring-boot-starter-validation`)
- Lombok for entity/boilerplate reduction (`@Data`, `@Builder`, `@RequiredArgsConstructor`, `@Slf4j`)
- Tests: JUnit **6** (via `junit-jupiter` 6.0.1, managed by the Spring Boot BOM), Mockito, AssertJ, ArchUnit 1.5.1 (version pinned in the root pom), `spring-boot-testcontainers`, `testcontainers-kafka`, H2 (in-memory, for lighter contexts), `@WebMvcTest` slice tests
- Jackson: global `SNAKE_CASE` property naming strategy (`application.yaml`) — all JSON request/response fields are snake_case even though Java fields are camelCase

## 4. Runtime configuration

- `application.yaml`: datasource points at `payments_db` on `payment` schema via Hikari, JPA `show-sql`/`format_sql` on, Redis on `localhost:6379`. Neither app runs Flyway at startup (migrations come from the `db-migrate` compose service), so an app started before the migrations finish fails on its first database access.
- `bootstrap.yml`: Vault client config (`localhost:8200`, dev token `root-token-local`, KV backend `secret`) — loaded before `application.yaml` per Spring Cloud bootstrap phase. Each app sets `spring.cloud.vault.application-name` to its own name, so it reads only its own secret (`secret/payment-producer-api`, `secret/payment-consumer-api`, `secret/payment-auth-server`; the last one also holds the OAuth2 client secrets as `app.auth.clients.<client>.secret`, and the auth server refuses to start without them); a missing secret does not fail startup (`fail-fast` is off) and the driver falls back to the OS user, which shows up as `role "<os user>" does not exist`.
- `src/test/resources/application-test.yaml`: H2 in-memory Postgres-compatibility mode, `ddl-auto: update` (schema generated by Hibernate for tests instead of Flyway).
- `docker-compose.yml` at repo root brings up **Postgres, Redis, Vault (+ a `vault-init` sidecar that seeds secrets), Kafka** (`apache/kafka:4.1.1`, single-node KRaft broker with dual `PLAINTEXT_HOST`/`PLAINTEXT` listeners for host and container access, no auth, no topics pre-created), **and Apicurio Registry** (`apicurio/apicurio-registry:3.3.2`, in-memory storage — no persistence, resets on restart). It also provisions **Zipkin, a Kafka exporter, Prometheus and Grafana** (see §3); Prometheus scrapes the apps on the host via `host.docker.internal`, authenticating as the `prometheus` OAuth2 client (`oauth2` block in `monitoring/prometheus/prometheus.yml`, client secret read from the mounted file `monitoring/prometheus/secrets/prometheus-client-secret`, which must match the Vault value); without `payment-auth-server` running the two application targets are `DOWN`. `monitoring/generate-traffic.sh` gets a token for `traffic-generator` and reads its secret from Vault.

## 5. Feature status — what actually works vs. what's a stub

### Implemented (Account domain, `AccountController` / `AccountService`)
- `POST /api/v1/accounts/` — create account, 201 + `Location` header, duplicate-number check (`DuplicatedAccountException` → 409)
- `PATCH /api/v1/accounts/{accountNumber}` — rename only, 204 (note: **not** `/accounts/{number}/owner` as the README claims)
- `DELETE /api/v1/accounts/{accountNumber}` — soft delete via bulk `UPDATE ... SET active = false`, 204, 404 if no rows affected
- `GET /api/v1/accounts/{accountNumber}` — active accounts only, `@Cacheable`
- `GET /api/v1/accounts` — paginated + `Specification`-based dynamic filtering (`AccountSpecification`), snake_case query params bound via `@BindParam`
- Redis cache-aside on lookup, evicted on rename/delete (`RedisCacheConfig.ACCOUNT_NAME` / `ACCOUNT_KEY`)
- Global exception handling (`GlobalExceptionHandler`): validation errors → structured field-level 400, `AccessDeniedException` (from `@PreAuthorize`) → 403, `AccountNotFoundException` → 404, `DuplicatedAccountException` → 409, `PaymentPublishException` → 503, catch-all → 500 (without the explicit 403 handler the catch-all would turn an access denial into a 500)
- Authorization (producer): every controller method has `@PreAuthorize` with the expressions in `security/Roles`: `ACCOUNT_READ` (both `GET`s), `ACCOUNT_WRITE` (`POST`, `PATCH`, `DELETE`), `PAYMENT_CREATE` (`POST /api/v1/payments`); `/actuator/health` is open, `/actuator/prometheus` needs `METRICS_READ`. No role hierarchy. Method security runs after argument binding, so an invalid request from a caller without the role gets 400, not 403. A request that changes state with no Bearer token gets 403 (CSRF is on and runs before authentication), reads get 401.

### Implemented (Payment domain, `PaymentController` / `PaymentService`)
- `POST /api/v1/payments` — validates the request, checks both `sourceAccount` and `targetAccount` exist via `AccountService#findByNumber` (reusing its `@Cacheable` lookup — no fresh query, no new cache), builds an Avro `PaymentEvent`, and publishes it synchronously (bounded by `app.kafka.producer.send-timeout`) to the `payment.events` topic. Returns 202 with a generated transaction id; 404 if either account doesn't exist; 503 if the broker doesn't confirm in time.
- The `KafkaTemplate<String, PaymentEvent>` is typed to the Avro-generated class, so nothing but a schema-conformant `PaymentEvent` can ever reach `.send(...)` from this codebase — enforcement happens both at compile time (the generic type) and at serialization time (Apicurio's `AvroKafkaSerializer` encodes strictly against the registered schema).
- `PaymentMethod` (domain enum, `common-libraries`) carries its Avro-generated counterpart per constant (`toAvroPaymentMethod()`) — the REST↔wire mapping lives in the enum itself, not in service code.

### Implemented (Payment consumer, `payment-consumer-api`)
- `PaymentEventListener` → `PaymentPersistenceService.persist` (checks `existsByTransactionId`, `saveAndFlush`, treats a unique-violation race as a duplicate). `PAYMENT` (Flyway V3) enforces unique `transaction_id`, FKs to `ACCOUNT(NUMBER)` for both accounts and `amount > 0`.
- `KafkaConsumerErrorHandlingConfig`: `DefaultErrorHandler` + `DeadLetterPublishingRecoverer` (templates keyed by value type: `PaymentEvent` via Avro, `byte[]` for poison pills), `ExponentialBackOffWithMaxRetries(maxAttempts - 1)`, `DataIntegrityViolationException` not retryable. Retry settings live in `KafkaConsumerProperties` (`app.kafka.*`, validated).
- Custom Kafka producers must apply `KafkaConnectionDetails` themselves (see `KafkaProducerConfig` and this config), otherwise Testcontainers' `@ServiceConnection` broker is ignored. `spring.kafka.bootstrap-servers` and the datasource URL are gated to the `!test` profile in the consumer. The consumer's `application-test.yaml` turns Flyway on and Vault off; its integration test runs the app pool as `payment-consumer-app` (`SET ROLE` through Hikari's `connection-init-sql`) while Flyway and fixtures use the container admin (`ConsumerDatabaseRoleConfiguration`). Consumer Testcontainers boot Postgres from the real `scripts/init-db.sql`, so roles and grants are the production ones; `DatabasePrivilegesTest` pins the privilege matrix.

- Events are published with **key = `transaction_id`** (`PaymentService`), so the key of a dead letter identifies the payment; events published before that change are keyed by the source account.
- The Avro namespace is `com.joaopbessa.payments.common.avro` (it used to be `com.joaopBessa…`). Messages written under the old namespace cannot be decoded any more, because Apicurio resolves the specific reader class by the writer schema's full name (Avro aliases do not help here). After pulling that change, reset the local Kafka volume (`docker compose down`, then remove `spring-kafka-payment-processor_kafka_data`) and flush Redis, whose cached values embed class names.
- `GET /api/v1/dead-letters` (consumer, port 8082) — returns the 10 oldest messages of `payment.events.DLT` (partition, offset, key, timestamp, decoded `payload` or `raw_payload` for poison pills), snake_case JSON (`spring.jackson.property-naming-strategy` is set in the consumer too). `DeadLetterReader` reads with `assign` + `seekToBeginning` on a throwaway `KafkaConsumer` (no group, no commits, `allow.auto.create.topics=false`), `DeadLetterPayloadDecoder` decodes through Apicurio, `DeadLetterService` returns domain `DeadLetterMessage`s (the controller maps them to `DeadLetterMessageResponse`), `DeadLetterViewConfig` wires the reader and decoder (bootstrap from `KafkaConnectionDetails.getConsumer()`). Needs the `DLT_VIEW` role (see below); no error classification and no account lookup by design. Read failures → 503 `ProblemDetail` (`DeadLetterExceptionHandler`), and so is an `AccessDeniedException` → 403 `ProblemDetail`.
- DLT replay (consumer): the DLT is the **backlog of pending messages**. `DeadLetterReplayScheduler` (`app.dlt-replay.*`, default `0 0 3 * * *` UTC, off in tests) calls `DeadLetterReplayService.replayPending()`: `DeadLetterReader.pending` snapshot → `DeadLetterReplayer` republishes original key/bytes/non-`kafka_dlt-*` headers to `payment.events` in offset order, stopping a partition at its first failure → `DeadLetterTruncator` (`Admin.deleteRecords`) removes the replayed prefix. A message that fails again returns to the DLT as a new record; no attempt limit yet. `POST /api/v1/dead-letters/replay` (`{"transaction_ids": [...]}`, 1–100 ids, 202 with `replayed`/`not_found`/`failed` per id, 400/503 as `ProblemDetail`, enabled via `spring.mvc.problemdetails.enabled`) republishes the most recent DLT record whose key is each id, reading the topic once; it does not truncate (the record is cleared by the next daily run, replayed again as an idempotent duplicate). Replays are counted in `payments_dead_letter_replayed_total{trigger,result}`.
- Authorization (consumer): `@PreAuthorize` with `security/Roles`: `DLT_VIEW` for `GET /api/v1/dead-letters`, `DLT_REPLAY` for `POST /api/v1/dead-letters/replay` (no hierarchy: replaying does not imply viewing); `/actuator/health` open, `/actuator/prometheus` needs `METRICS_READ`. Same status rules as the producer (401 for reads without a token, 403 for writes without a Bearer token because of CSRF, 403 without the role). The Kafka listener and the scheduled replay do not go through HTTP, so they are not affected. `DeadLetterReplayService` takes the batch size as a plain `int`, and its bean (with the replayer and truncator) is declared in `DeadLetterReplayConfig`. Single-instance assumption (no distributed lock).

### Implemented (Authorization server, `payment-auth-server`)
- `DatabaseUserDetailsService` loads users from `APP_USER`/`APP_USER_ROLE` (`AppUserRepository`, entity `AppUser`); the stored `{base64}...` password goes to the `DelegatingPasswordEncoder` bean from `common-libraries` (Base64 is an encoding, not a hash, and the Javadoc and READMEs say so); disabled users stay disabled.
- `AuthorizationServerConfig` declares two chains (authorization server endpoints; form login with `/actuator/health` and `/error` open via `OpenEndpoints`) and registers the clients in memory from `AuthServerProperties` (`app.auth.*`, validated, `toString` hides the secrets): `payments-cli` (public, PKCE required), `prometheus` (`METRICS_READ`), `traffic-generator` (producer roles). `RolesClaimCustomizer` writes the `roles` claim of access tokens only. The authorization server's own `/oauth2/*`, `/.well-known/oauth-authorization-server` and `/oauth2/jwks` (public key only) are served by Spring Authorization Server.
- `scripts/get-token.sh <user> <password>` runs the authorization code + PKCE flow without a browser and prints the token. Demonstration users and their roles are in `payment-auth-server/README.md`.
- Tests worth knowing: `AuthorizationServerIntegrationTest` runs the pool as `payment-auth-app` (`SET ROLE`, like the consumer) on a real Postgres with the production `init-db.sql` and Flyway migrations; its test client secrets live only in `src/test/resources/application-test.yaml`.

### Stub / not implemented
- No mapper layer (README describes a `mapper/` package with MapStruct; in reality DTOs do their own mapping via static factory methods / instance `toEntity()` — MapStruct is not even a dependency).
- No service interface + impl split (README describes `service/impl`; actual code is a single concrete `AccountService` class).
- No alerting (Alertmanager) and no Kafka monitoring UI.
- No Cucumber/BDD tests despite being in the roadmap and README testing-strategy table.

## 6. Package & naming conventions (and inconsistencies to watch)

- Base package and Maven `groupId` are `com.joaopbessa.payments…` in every module, all lower case (the Java and Maven convention). `PackageNamingTest` (one per module, backed by the `PackageNaming` helper in the `common-libraries` test-jar) fails if a main, generated or test package gets an upper-case letter.
- Layering inside `payment-producer-api`: `api.dto.request` / `api.dto.response`, `controllers`, `services`, `domain.entities`, `repositories` (+ `repositories.specifications`), `exceptions`, `config`. This is a flatter layout than the `controller/v1`, `service/impl`, `mapper` structure documented in the README — the README describes a target structure, not the current one.
- The dependency rules are enforced by an `ArchitectureTest` (ArchUnit) in each app: no package cycles; in the producer `repositories` and `domain` stay free of `api`, only the controllers use the services, every public `@RestController` method carries `@PreAuthorize` (a new endpoint cannot ship unprotected) and `domain`/`repositories`/`services` stay free of `security`; in the consumer `dlt` imports neither `config`, `api` nor `security`, the payment pipeline (`domain`, `repositories`, `mappers`, `services`, `listeners`) stays free of the web layer, `dlt` and `security`, `metrics` depends on nothing of the application, and every public `@RestController` method carries `@PreAuthorize` as in the producer. Map to DTOs in the controller layer, and pass configuration values into `dlt` classes instead of importing `*Properties`. In the auth server `domain`/`repositories` stay free of `security`, `tokens` and `config`, `tokens` depends on none of them, and only `config` may use `AuthServerProperties` (the one that holds client secrets). If a rule fails, fix the dependency; do not weaken the rule.
- Source, logs, comments, scripts and `.gitignore` are in English.
- DTOs are Java `record`s; entities are Lombok classes (`@Data @Builder @AllArgsConstructor @NoArgsConstructor`) — standard, intentional split between immutable transport objects and mutable JPA entities.
- Route inconsistency: `POST /api/v1/accounts/` has a trailing slash; every other account route does not.
- Custom runtime exceptions (`AccountNotFoundException`, `DuplicatedAccountException`) both declare an unused `serialVersionUID` on a `RuntimeException` subtype — harmless but not idiomatic (that field matters for `Serializable`, not for exceptions used purely in-process).

## 7. Build, run, test

```bash
# From repo root — build all modules
mvn -B clean verify

# Run the apps locally (requires `docker compose up -d --wait` first: postgres, db-migrate, redis, vault, kafka, apicurio;
# confirm migrations with `docker compose ps -a db-migrate` — `up -d` returns 0 even if the one-shot migration fails)
# `init-db.sql` only runs on an empty volume; to pick up new roles: docker compose rm -sf postgres && docker volume rm spring-kafka-payment-processor_postgres_data
# The producer listens on 8081 (8080 is Apicurio's host port); the consumer listens on 8082 (Actuator and the dead letter endpoints)
cd payment-producer-api && mvn spring-boot:run
cd payment-consumer-api && mvn spring-boot:run
# The authorization server listens on 9000 (needs its Vault secret and the `payment-auth-app` role, see its README)
cd payment-auth-server && mvn spring-boot:run

# Single module: `-pl <module>` resolves the sibling modules from ~/.m2, so a stale installed snapshot (for example
# a `payment-db-migration` without the newest Flyway versions) fails in confusing ways. Use `-am`, or run
# `mvn -q install -DskipTests -pl common-libraries,payment-db-migration` first.

# Run tests only
mvn test
```

CI (`.github/workflows/maven.yml`): GitHub Actions on push to `main`/`develop` and on PRs, `ubuntu-latest`, Java 21 (Temurin), 15-minute timeout, `TZ=UTC`, runs `mvn -B clean verify` with `SPRING_CLOUD_VAULT_ENABLED=false` and `SPRING_CLOUD_BOOTSTRAP_ENABLED=false` (Vault is not available there). Docker is preinstalled on the runner, so Testcontainers works without extra setup. To reproduce CI locally, stop `docker compose` first (a running local Kafka/Redis can mask Testcontainers wiring bugs) and export the same env vars.

### Test conventions in place
- `ArchitectureTest` in each app uses the plain `com.tngtech.archunit:archunit` artifact (rules called with `.check(classes)` inside ordinary `@Test` methods, test classes excluded from the import). ArchUnit fails a rule that matches no class, so a renamed package cannot silently empty a rule.
- Do not write test counts in the READMEs or here: they go stale. The CI job summary (`scripts/test-summary.sh`, which reads the surefire reports) publishes the real totals of every run; run it locally after `mvn verify` to see them.
- `@WebMvcTest` slices for controllers, mocking the service layer with `@MockitoBean`, asserting on `MockMvc` + `jsonPath`. A slice only gets the security configuration if it imports it: producer slices use `@Import({ ResourceServerSecurityAutoConfiguration.class, TestJwtConfiguration.class })` and send `issuer.bearer(roles)` (`TestJwtIssuer` from the `common-libraries` test-jar signs the tokens, `TestJwtConfiguration` registers the matching `JwtDecoder`); the role matrix lives in `AccessControlTest`, the other controller tests just call as an authorized user. The consumer is the same, and its integration tests call through `BearerRestClient` (a `TestRestTemplate` plus the issuer, registered by `BearerRestClientConfiguration`); a call without credentials uses the plain `TestRestTemplate`.
- Producer `TestcontainersConfiguration` provisions Kafka (`apache/kafka:4.1.1`) and Redis via `@ServiceConnection`, plus a `GenericContainer` for Apicurio Registry whose URL is exposed through a `DynamicPropertyRegistrar` bean (no Boot `ConnectionDetails` factory exists for Apicurio). The consumer has its own `PostgresContainerConfiguration` and `KafkaInfrastructureConfiguration` with the same pattern.
- Integration tests must read broker addresses from `KafkaConnectionDetails`, never from `spring.kafka.bootstrap-servers` (the Testcontainers broker is not a property).
- H2 (`application-test.yaml`) used for lighter contexts that don't need a real Postgres/Testcontainers instance
- `TestPaymentProducerApiApplication` — a Testcontainers-friendly bootstrap entrypoint for local dev (`SpringApplication.from(...).with(TestcontainersConfiguration.class).run(...)`)
